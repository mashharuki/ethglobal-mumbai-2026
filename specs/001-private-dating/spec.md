# Feature Specification: プロフィールを公開せずに相手と出会う

**Feature Branch**: `create_spec`  
**Created**: 2026-11-06  
**Status**: Draft  
**Input**: 匿名で相性条件を確認し、二人で場面を体験してから会うかを選ぶ。登録時に預けたステーブルコインは、対面後の双方の確認に従って精算する。[企画・構成図・計画への引継ぎ](planning-input.md)

本機能は3分冊で管理する。各FRの正式な本文は主担当の仕様に一度だけ置く。以下の共通ストーリー、SC、決定履歴、前提条件は3領域を結合したときの受入基準とする。Spec Kitで計画・分析・実装するときは、この入口と3分冊を合わせて読む。

| 担当別仕様 | 主担当の要件 | 他領域へ渡すもの |
| --- | --- | --- |
| [フロントエンド](frontend.md) | FR-001、FR-004、FR-008 | 端末で検証した照合結果、登録証明、本人の署名と選択。相性結果は当事者だけが利用する |
| [バックエンド](backend.md) | FR-002、FR-006、FR-007 | 公開可能な現行登録版、暗号文配送の状況、非公開の部屋資格・確定した手番 |
| [スマートコントラクト](smart-contract.md) | FR-003、FR-005、FR-009、FR-010、FR-011、FR-012 | 入金・両預託の拘束・精算・受領の確定状態。APIと端末はこの状態を参照する |

変更時は該当FRの主担当文書を起点に、受け渡し先と共通シナリオを見直す。通信形式は[サービス契約](contracts/service.md)、二者照合は[照合契約](contracts/matching.md)、資金の操作は[精算契約](contracts/settlement.md)を参照する。

## Clarifications

### Session 2026-11-06

- Q: 初版の相性条件は？ → A: 双方が判定を許可した趣味に一つ以上の共通項があること。
- Q: 対面後の虚偽確認で預託金の分配対象にできる登録項目は？ → A: 職業と年齢帯の2項目。
- Q: 対面時に登録していた職業・年齢帯をどう確認する？ → A: 本人が選んだ項目だけを本人の端末で提示し、マッチ成立時の登録版との一致を確認する。
- Q: 第三者は二人の趣味の一致やマッチ成立を確認できる？ → A: 公開は各仮名の登録証明まで。ペアの一致・成立は当事者だけに直接示し、公開送金から推測され得ることを事前に説明する。
- Q: 新しい相手を見つけるには、二人が同時に検索している必要がある？ → A: 双方が「相手を探す」を開いている間だけ新しい候補を見つける。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 個人情報を見せずに相手を見つける (Priority: P1)

参加者は趣味・暮らし方・交際に望むことを自分の端末に入力し、照合に使ってよい趣味を選ぶ。相手に見える項目と預託条件を確認してから登録する。双方が「相手を探す」を開き、共通の趣味が見つかれば仮名で招待を送り、二人が希望したときだけマッチが成立する。

**Why this priority**: 相手の属性を並べた一覧を作らずに、知り合うきっかけを作るため。  
**Independent Test**: 架空の3人に、一致する組と一致しない組を用意する。登録から招待の承諾まで進め、各参加者・運営・公開先が受け取る情報を比較する。

**Acceptance Scenarios**:

1. 初回登録者が預託を確認すると、選んだ銘柄・数量・返却期限の計算方法・没収時の内訳・公開される情報が表示される。入金確定後に期限日時を表示し、登録にも成功すると候補に参加できる。入金後に登録が失敗した場合、本人は未拘束の預託を直ちに取り消して全額回収できる。
2. 二人が同時に「相手を探す」を開き、二人の登録内容が「共通の趣味が一つ以上」という双方が許可した条件を満たすと、仮名と条件成立の証明を確認できる。趣味の具体名は二人の間で送受信されず、第三者に公開される記録にも含まれない。
3. 許可済み趣味に共通項がない組（交際目的だけが一致する組を含む）、または証明を別の参加者のものと入れ替えた組は候補にならない。招待の拒否ではマッチも資金の移動も発生しない。
4. 第三の参加者は各仮名の登録を確認できる。どちらの仮名で検索しても、二人の組・一致結果・成立状況は返らない。
5. 双方の承諾後は拘束確認中と表示する。署名した両登録版・両預託・共通期限どおりに両方の拘束が確定した招待だけが成立し、部屋資格を発行できる。取引失敗・期限切れ・競合で拒否された招待は不成立とし、部屋資格を発行しない。後から別の版に差し替えて精算対象にすることはできない。

### User Story 2 - 対面後の確認をもとに預託金を受け取る (Priority: P1)

二人は会って話した後、それぞれ自分の判断を提出する。分配対象は、登録時に双方が自己申告した「職業」と「年齢帯」の2項目。預託前にこの範囲を表示する。対面では各自が選んだ項目を自分の端末で相手に見せる。例えば職業だけを選ぶと、その登録値とマッチ時の版との一致結果が表示され、年齢帯は伏せたままになる。好みの違いやシミュレーション中の選択には金銭的なペナルティを課さない。

**Why this priority**: 資金を預ける前に、一方的な訴え、不一致、無回答のそれぞれで何が起こるかを説明できることが参加の前提になる。  
**Independent Test**: 銘柄の異なる預託を持つ成立済みマッチを用意し、次の各例で両者と運営の受取額を確認する。

**Acceptance Scenarios**:

| 対面後の状態 | 期待する精算 |
| --- | --- |
| 双方が「問題なし」と期限内に確定 | それぞれに元の銘柄・数量を全額返す。運営の受取はゼロ。 |
| Aが100単位のX、Bが40単位のYを預け、双方が同じ事実項目についてAの虚偽と確定 | Bは補償として90 X、自身の返却分として40 Yを受け取る。運営は10 X、Aの返却はゼロ。 |
| AだけがBを申告、判断が食い違う、責任者や対象項目が違う（一人は職業、もう一人は年齢帯を指摘）、またはどちらかが無回答 | 期限内は未精算。期限以降は追加の相手承認を必要とせず、それぞれに全額返却できる。 |
| 会わなかった、または双方が終了を選んだ | 双方の合意終了なら即時に全額返却。片方だけの終了なら期限以降に全額返却できる。 |
| 第三者による回答、別のマッチの回答、期限以降に届いた没収指示、精算済み操作の再送 | 不正な指示は受理せず、確定した配分は変わらない。二重に支払われない。 |

### User Story 3 - 二人で場面を体験し、会うかを選ぶ (Priority: P2)

マッチした二人は任意でターン制のシミュレーションを始める。例えば雨で予定を変更する場面で、一人が「屋内の場所を探す」を選び、もう一人が「一緒に候補を選ぶ」と応じる。次の場面には二人が屋内で過ごす選択が反映される。

**Why this priority**: プロフィールの比較では分からない、相談の仕方や相手の考え方を知る機会を作る。  
**Independent Test**: 成立済みの架空のペアで2ターンを体験する。同じ開始場面で異なる選択をした場合に、それぞれの選択と矛盾しない次の場面が表示されることを確認する。

**Acceptance Scenarios**:

1. 双方が参加を選ぶと最初の場面が届く。一人目の選択後は相手の応答待ちとなり、二人が回答して初めて場面が進む。
2. 再接続すると同じ場面・手番から再開できる。連打や場面生成の再試行でも選択を二重に適用しない。
3. どちらも途中で離脱できる。対面を希望するかは各自が別に選び、双方が希望した場合だけ相手に成立を知らせる。参加、離脱、対面希望そのものでは資金は移動しない。

### Edge Cases

- 新しい候補を探す間に相手が検索を終了・切断した場合、その相手との未完了の照合から候補を追加しない。双方が再び検索を開始すると、新しい照合に参加できる。検索終了だけでは成立済みマッチや預託の状態は変化しない。
- マッチ前の登録取消は全額返却。預託期限にマッチがなければ同様に返却可能。同じ預託を同時に二つのマッチに割り当てない。
- 預託や払出しの成否が不明なら「確認中」と表示する。再開時に同じ預託・受取の状況を確認でき、未受領分は完了扱いにしない。
- 端数がある場合は運営の10%を銘柄の最小単位で切り捨て、残りを被害者に渡す。例として最小単位101なら被害者91、運営10。
- 部外者によるセッション閲覧、手番の横取り、別の組での証明の使い回しは拒否する。予定や実名の自由記述は初版の入力対象外。

## Requirements *(mandatory)*

### Functional Requirements

機能要件の正本は冒頭の担当表に示す[フロントエンド](frontend.md)、[バックエンド](backend.md)、[スマートコントラクト](smart-contract.md)の3仕様。担当をまたぐ要件の合否は上記の受入シナリオで判定する。

### Key Entities

| 対象 | 意味 |
| --- | --- |
| 非公開プロフィールと申告の版 | 本人だけが保有する事実・好みと、マッチ時に双方が参照する登録版。 |
| 仮名と公開の登録証明 | その仮名で参加登録していることを第三者が確かめる材料。 |
| ペアの相性証明 | 共通の趣味があることを対象の二人が確認する材料。各人の登録版に結び付く。 |
| マッチ | 双方の承諾、登録版、二人の預託、精算期限を結ぶ単位。 |
| 共同セッション | マッチごとの共有テーマ、場面、手番、選択履歴、参加状態。 |
| 預託・対面後の確認・精算 | 所有者別の銘柄と実受領数量、双方の確定回答、受取人別の権利と支払状況。 |

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001** 初見の参加者5人中4人以上が、操作説明を受けずに5分以内に登録を完了し、相手に見える情報と自分だけが保持する情報を一つずつ正答する。外部の送金確定待ちは別計測とする。
- **SC-002** 既知の入力を持つ一致・不一致・登録版差し替え・別人の証明・片方が検索を終了した場合の5例すべてで、期待する組だけが候補になる。相手、運営、公開記録、場面生成先で電子的に受け取る登録時の非公開値は各0件とする。先行実証は独立した2台で本物の証明を生成・検証し、一致・不一致を各1回以上再現する。検索開始から結果表示までの実時間と端末別の生成・検証時間を記録する。動画尺による秒数制限は設けない。対面提示で職業だけを選んだ場合、本人端末の提示画面に表示される年齢帯は0件とする。
- **SC-003** テスト参加者5組中4組以上が、最初の場面から3分以内に2ターンを完了し、自分たちの選択が次の場面にどう反映されたか一例を説明できる。
- **SC-004** Story 2 と Edge Cases の各精算例で、受取人ごとの銘柄・数量が期待値に100%一致する。追加検証では銘柄の異なる預託、端数、同時請求、再送、期限の直前と期限ちょうどを含める。

## Assumptions

- ETHGlobal Mumbaiの **Start Fresh（Classic / From Scratch）** 部門に応募予定。提出期限は **2026年11月7日（土）09:00 IST（インド時間）**。これは大会提出の期限で、下記の預託金の精算期限とは別に管理する。[公式提出案内](https://ethglobal.com/events/mumbai/info/details)
- 審査では、二人が検索を開き、個別の趣味を送らずに共通点の有無を確認する場面を示す。公開可能な仮名の登録証明と、当事者だけが確認する照合結果を区別する。指定された証明技術、実証の条件、応募候補の賞は[計画への引継ぎ](planning-input.md)を参照する。
- 初版は成人のテスト参加者、架空のプロフィール、テスト用の資金を使う。実運用での年齢・身元確認は別途扱う。
- 預託量の指定がないため、初版は本人が選んだ一銘柄の正の数量を受け付ける。最小価値の保証や為替換算は行わず、相手の預託条件をマッチ承諾前に確認できる。銘柄の違いはマッチ成立を妨げない。
- 各預託の期限は、確定した入金取引を含むブロックの時刻から7日（604800秒）後。登録の成功や再試行で起算点は変わらない。二人の期限が異なる場合は早い方をマッチの期限として、双方の承諾前に表示する。時刻はデモで再現可能とする。
- 客観的に話し合える登録項目と主観的な好みを区別する。登録時の職業・年齢帯は前者、「会話が楽しい」は後者。事実確認を担うのは対面した二人であり、虚偽を申告した側が認めない場合も、不一致時の返却条件を適用する。
- 端末での証明作成、公開記録の読取、場面生成、預託の確認が利用できることが各体験の前提。場面生成が停止しても対面後の確認と返却手続きには進める。
