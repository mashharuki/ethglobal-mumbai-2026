# Feature Specification: プロフィールを公開せずに相手と出会う

**Feature Branch**: `create_spec`  
**Created**: 2026-11-06  
**Status**: Draft  
**Input**: 匿名で相性条件を確認し、任意で承認済みPersonaとのAI会話を試してから会うかを選ぶ。登録時のステーブルコインは、合意終了または固定期限に各自の元本として返却する。[企画・構成図・計画への引継ぎ](planning-input.md)

**採用した優先順（2026-11-06）**：①ENSの権限分離・独立検証と根拠付きの資格停止/異議/回復 → ②希望条件を含む二者照合 → ③多人数の候補選択。詳細は[Plan](plan.md)の段階A/B/C。マッチ用預託は元本返却専用へ変更し、旧90/10配分・運営の罰金収入を廃止する。独立保証金・新しい没収・検討用の金額例は採用しない。全体はDraft。親側は未実装、AIBotは単体実装済み・親結合未確認。

本機能は3分冊で管理する。各FRの正式な本文は主担当の仕様に一度だけ置く。以下の共通ストーリー、SC、決定履歴、前提条件は3領域を結合したときの受入基準とする。Spec Kitで計画・分析・実装するときは、この入口と3分冊を合わせて読む。

| 担当別仕様 | 主担当の要件 | 他領域へ渡すもの |
| --- | --- | --- |
| [フロントエンド](frontend.md) | FR-001、FR-004、FR-008、FR-016 | 非公開照合、本人の終了署名、停止理由/異議/ブロックの本人UI |
| [バックエンド](backend.md) | FR-002、FR-006、FR-007、FR-013、FR-014、FR-015 | 現行資格・利用枠、私的な審査と回復、暗号文配送・候補割当・AIBotへの認証/マッチ連携 |
| [スマートコントラクト](smart-contract.md) | FR-003、FR-005、FR-009、FR-010、FR-011、FR-012 | 入金・両預託の拘束・精算・受領の確定状態。APIと端末はこの状態を参照する |

変更時は該当FRの主担当文書を起点に、受け渡し先と共通シナリオを見直す。通信形式は[サービス契約](contracts/service.md)、二者照合は[照合契約](contracts/matching.md)、資金の操作は[精算契約](contracts/settlement.md)を参照する。

| 判定ID・目標賞 | 主担当 | 本製品の実演とタスク |
| --- | --- | --- |
| EF-CROPS — Best CROPS App | Web/ZK担当 | 2端末の非公開照合と第三者が得る情報を検証する。T017・T031・T035 |
| ENS-V2 — Best Use of ENSv2 | API担当 | 資格と本人用キーの権限分離・独立検証・失効を示す。T037〜T039・T041・T042・T034。製品登録への結合はT014・T015 |
| ARKIV-APP — Build on Arkiv (from scratch) | Arkiv担当（API領域） | 公開登録の書込から利用者画面の実読取までを示す。T014・T015・T032 |

提出担当はT036で3件を個別判定する。EF内の追加応募EF-RPCとArkiv内の追加候補ARKIV-SWARMは実証時のみ選択でき、正式な3提供元は変わらない。詳細な技術条件と提出物は別紙に集約する。

## Clarifications

### Session 2026-11-06

- Q: 初版の相性条件は？ → A: 当初は共通趣味のみ。ブース後の優先順位決定により、双方の希望条件も満たすことを追加する。最小の希望条件は性別・交際目的とし、双方の自己申告と許容する相手の条件を区別する。
- Q: 対面後の虚偽確認で預託を分配するか？ → A: 当初の職業/年齢帯に基づく90/10案は廃止。選択提示は維持するが、マッチ預託は各自の元本返却専用にする。
- Q: 対面時に登録していた職業・年齢帯をどう確認する？ → A: 本人が選んだ項目だけを本人の端末で提示し、マッチ成立時の登録版との一致を確認する。
- Q: 第三者は二人の趣味の一致やマッチ成立を確認できる？ → A: 公開は各仮名の登録証明まで。ペアの一致・成立は当事者だけに直接示し、公開送金から推測され得ることを事前に説明する。
- Q: 新しい相手を見つけるには、二人が同時に検索している必要がある？ → A: 双方が「相手を探す」を開いている間だけ新しい候補を見つける。
- 決定：Ethereum Foundation・ENS・Arkivを正式な応募目標とし、各賞の担当・実演・提出判断を仕様とタスクで管理する。これは応募方針の確定であり、機能全体のDraft状態や実装完了を変更しない。
- 決定：ENS資格検証を入金・プロフィール証明から独立して先行実証する。二者照合、多人数候補選択の順に結合し、資格だけで本番の検索やマッチ成立を許可しない。追加決定：評判は参加状態として扱い、根拠通知・異議・回復まで採用する。新しい没収は採用せず、運営の罰金収入を含む旧90/10は廃止して元本返却へ移す。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 個人情報を見せずに相手を見つける (Priority: P1)

参加者は趣味、自己申告の性別・交際目的、希望する相手の条件を自分の端末に入力する。参加資格を検証し、公開範囲と預託条件を確認して登録する。双方が「相手を探す」を開き、双方の希望と共通趣味の条件を満たせば仮名で招待を送り、二人が希望し両預託が拘束されたときだけ成立する。別クライアントでも参加資格を検証できる。

**Why this priority**: 相手の属性を並べた一覧を作らずに、知り合うきっかけを作るため。  
**Independent Test**: 段階Aは入金なしで資格と審査による停止/回復を2実装から検証する（SC-005/007）。段階Bは独立2端末の合成入力で希望条件と趣味を照合する（SC-002）。段階CはN=10/50の候補割当を検証する（SC-006）。製品結合では登録から招待の承諾・拘束まで進め、各者が受け取る情報を比較する。

**Acceptance Scenarios**:

1. 初回登録者が預託を確認すると、選んだ銘柄・数量・返却期限の計算方法・各自への全額返却・公開される情報が表示される。入金確定後に期限日時を表示し、登録にも成功すると候補に参加できる。入金後に登録が失敗した場合、本人は未拘束の預託を直ちに取り消して全額回収できる。
2. 両者の資格が有効で同時検索中、双方の希望条件を満たし、許可済み趣味が一つ以上共通するときだけ候補になる。表示は仮名と条件全体の成立まで。趣味・性別・交際目的の実値、共通件数、どの条件が不一致かを返さない。真偽と自分の条件から推測できることは事前に説明する。
3. 趣味だけの一致、片方向だけの希望一致、共通趣味ゼロ、別人・別版の証明では候補にしない。「指定なし」は当該希望条件を制限しないが、共通趣味の要件は残る。招待の拒否ではマッチも資金の移動も発生しない。
4. 第三の参加者は各仮名の登録を確認できる。どちらの仮名で検索しても、二人の組・一致結果・成立状況は返らない。
5. 双方の承諾後は拘束確認中と表示する。署名した両登録版・両預託・共通期限どおりに両方の拘束が確定した招待だけが成立し、マッチ参加資格を発行できる。取引失敗・期限切れ・競合で拒否された招待は不成立とし、マッチ参加資格を発行しない。後から別の版に差し替えて精算対象にすることはできない。
6. 本人は接続先・公開鍵を更新できるが資格参照を変更できない。独立した別クライアントも同じ有効資格を受理し、停止・失効・古い資格を拒否する。これは本人性や誠実さの自動判定ではない。
7. N人の検索では各人の1ラウンドの割当をK人以内とする。自己照合・同一ペアの重複・終了リースを除き、属性を平文索引に使わない。照合未実施の相手を「不一致」と表示しない。

8. 通報だけでは相手を全体から停止しない。根拠付きの合成決定で停止した本人は理由・期限・異議を確認でき、取消や停止期限到来で回復する。新しい資格版を別クライアントも検証し、資金返却は変わらない。

### User Story 2 - 合意終了または固定期限に元本を回収する (Priority: P1)

参加者は対面・交際・継続を断ることができる。職業/年齢帯の選択提示は本人の端末内で行い、提示内容や相手の評価を金銭配分に使わない。双方が終了に合意すれば期限前に各自へ全額返却し、合意がなくても固定期限に各自が単独で元本を回収する。

**Why this priority**: 通報・資格停止・異議・相手の不応答があっても、資金を取り戻す条件が変わらないことを預託前に説明できる必要がある。

**Independent Test**: 成立済み合成マッチで、各銘柄・所有者ごとの元本が保存され、運営と相手への付替えが拒否されることを確認する。

**Acceptance Scenarios**:

| 状態 | 期待する返却 |
| --- | --- |
| Aが100 USDC、Bが40 EURCを預け、双方が期限内に終了へ署名 | Aに100 USDC、Bに40 EURC、運営に0。対面の有無は条件にしない |
| 片方が終了を望まない・無回答、または通報/反証/異議の途中 | 期限前の一方的な拘束解除はしない。固定期限ちょうど以降は各自が相手の承認なしで元本を全額回収 |
| 資格停止、本人ブロック、ENS/API/モデルの停止 | 既存の復元・返却経路を維持。停止や審査を理由に元本を減らさず期限を延ばさない |
| 未拘束の預託、入金後の登録失敗 | 本人が即時に全額取消できる |
| 旧90/10指示、相手/運営への付替え、別マッチの署名、二重受領 | 拒否。期限ちょうどは合意終了でなく期限返却を通す |

### User Story 3 - 任意でPersonaと会話し、会うかを選ぶ (Priority: P2)

成立したマッチの本人は、相手が利用を認めたPersonaとAI会話を試せる。Personaの本人は、インタビューの送信、抽出・校正・修正、保存と相手の利用を個別に確認する。3シーンの自由会話を通して会う前のきっかけを作る。AIの返答は本人の約束や実際の意思ではない。

**Why this priority**: 完成済みのAIBotを再利用し、写真以外の接点を任意で提供する。二人同時の共同体験は後続へ移す。

**Independent Test**: 架空の成人Personaと成立済みマッチで、本人引継ぎ・同意→会話→申請を[接続契約](contracts/simulation.md)どおり検証する。単体の架空マッチと実マッチ結合を区別する。

**Acceptance Scenarios**:

1. 本人とPersona所有者の現行同意がある正しいマッチだけを開始できる。照合用の秘密入力をAIへ自動転送せず、AI用の入力・送信先を別画面で確認する。
2. 自由会話・Retry・3シーンの進行・同意撤回を選べる。別主体/Persona/期限切れ/ブロックを拒否し、モデル停止と定型デモを区別する。再起動後の復元は保証せず再認証/再開始を表示する。
3. デート申請は同一ゲームからの再送でも一件とし、相手の独立した承諾までpending。AIの返答・申請・会話の終了だけでは連絡先公開や資金移動を起こさない。

### Edge Cases

- 資格は候補確定・双方承諾の受付時に再検証する。停止前に調整用APIが受付ID・拘束digest・短い有効期限へ固定した操作だけは、期限内に拘束確定すれば既存マッチとして扱う。停止後の新規受付・内容変更・期限切れは拒否する。本人の「送信済み」という申告では判定しない。既存の資金・救済へのアクセスは維持し、ブロックされた相手からの新規接触は止める。
- 新しい候補を探す間に相手が検索を終了・切断した場合、その相手との未完了の照合から候補を追加しない。双方が再び検索を開始すると、新しい照合に参加できる。検索終了だけでは成立済みマッチや預託の状態は変化しない。
- マッチ前の登録取消は全額返却。預託期限にマッチがなければ同様に返却可能。同じ預託を同時に二つのマッチに割り当てない。
- 預託や払出しの成否が不明なら「確認中」と表示する。再開時に同じ預託・受取の状況を確認でき、未受領分は完了扱いにしない。
- 原単位101の預託も本人へ101返す。率による配分・丸めや運営受取はない。通報や対面の評価を精算入力に含めない。
- 部外者によるAIセッション閲覧、別主体/Persona/マッチの差替え、期限切れの本人引継ぎは拒否する。AIBotの自由会話は別の送信同意を必要とし、MVPでは架空の成人データだけを使用する。プロセス再起動後の復元は保証せず、再認証/再開始を案内する。

### Functional Requirements

機能要件の正本は冒頭の担当表に示す[フロントエンド](frontend.md)、[バックエンド](backend.md)、[スマートコントラクト](smart-contract.md)の3仕様。担当をまたぐ要件の合否は上記の受入シナリオで判定する。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001** 初見の参加者5人中4人以上が、操作説明を受けずに5分以内に登録を完了し、相手に見える情報と自分だけが保持する情報を一つずつ正答する。外部の送金確定待ちは別計測とする。
- **SC-002** 合成入力の10例（全条件一致、共通趣味ゼロ、Aの性別希望不一致、Bの性別希望不一致、Aの目的希望不一致、Bの目的希望不一致、双方指定なし、登録版差し替え、別人の証明、片方の検索終了）で、期待する組だけが候補になる。独立2端末で実証明を生成・検証し、秘密値・共通件数・条件別の成否を出力しない。真偽からの推測可能性は別に記録する。検索開始から表示まで、端末別生成・検証時間と通信量を記録し、動画尺で制限しない。対面提示で職業だけを選んだ場合、年齢帯は表示しない。
- **SC-003** 架空の成人データで初見5人が承認済みPersonaとの2往復を試し、4人以上が送信前確認から3分以内（外部推論待ちは別計測）に完了し、AIへ送る情報と任意性を説明できることを目標とする。別途、3シーン9ターン、Retry、撤回/ブロック後の拒否、別主体/Persona/期限切れ拒否、モデル停止、申請冪等、再起動時の再開始を検証する。作者の単体試験を親結合の合格に代えない。
- **SC-004** Story 2と境界ケースの全例で、各所有者へ原銘柄・元本が100%返り、相手/運営/審査者への付替えが0件である。2銘柄、101原単位、未対応資産、同時請求、再送、旧90/10指示、期限直前/ちょうど/以降、停止/異議/ブロック/サービス停止中を含める。
- **SC-005** [参加資格契約](contracts/participation.md)の正負例が2つの独立した読取実装で一致する。本人用キーの更新は成功し、資格改ざん・権限迂回・失効した委任鍵・停止/期限切れ/旧版/再発行前/別発行者の資格は拒否する。AのBFF停止中もBが検証できる。取引・確認ブロック・版・読取経路を記録し、固定表示を成功に数えない。
- **SC-006** N=10/50、K=3、同時実行上限=1を初期fixtureとして、各10ラウンドの候補割当を再現する。各人の割当数・同時数超過、自己照合、同一ペア/同一版の重複、終了リースへの新規割当は0件。待ち時間・割当数の偏り・切断復帰・再送・通信量を記録する。新規枠1・ブロックしたペアの除外は追加例で確認する。模擬暗号でのスケジューラ試験と、SC-002の実暗号性能を別に表示し、全員との照合や最適マッチは保証しない。

- **SC-007** [資格審査契約](contracts/participation-review.md)の全受入例を合成データで再現する。署名付きtier更新と枠判定fixture、通報だけで停止しないこと、根拠通知・権限/利益相反の拒否、異議による回復、期限ちょうど、別の停止が残る取消、旧版/再発行の拒否、非公開項目の公開0件を確認する。実際の割当への枠/ブロック反映は段階C、資金不変はSC-004で別に検証し、実世界の事実認定を実証したとは扱わない。

- 2分プレゼンはキャッチコピー→利用者の流れ→技術の役割の順とする。技術実装は資格の独立検証、希望条件を含む二者照合、多人数の候補割当の順を維持する。公開資格・登録証明と当事者だけの照合結果を区別する。採用した優先順は実装完了を意味しない。技術指定は[計画への引継ぎ](planning-input.md)、賞別条件は[応募目標](prize-targets.md)を参照する。
- 最小の希望条件は性別と交際目的。自己申告は各辞書内の単一値、相手への希望は許容値の集合または指定なしとする。辞書はT002で合成試験用に版固定し、一般利用者向け分類の確定とは扱わない。肌の色、生活リズム、自由記述による分類は今回追加しない。
- 初版は成人のテスト参加者、架空のプロフィール、テスト用の資金を使う。実運用での年齢・身元確認は別途扱う。
- 預託量の指定がないため、初版は各自がUSDC・EURCのどちらか一銘柄を選び、その正の数量を受け付ける。最小価値の保証や為替換算は行わず、相手の預託条件をマッチ承諾前に確認できる。銘柄の違いはマッチ成立を妨げない。
- 各預託の期限は、確定した入金取引を含むブロックの時刻から7日（604800秒）後。登録の成功や再試行で起算点は変わらない。二人の期限が異なる場合は早い方をマッチの期限として、双方の承諾前に表示する。時刻はデモで再現可能とする。
- 職業・年齢帯の選択提示は自己申告と登録版の一致までを示す。現実の真偽や故意は証明しない。合成ケースで資格審査の手続きを検証し、現実の違反検出・裁定能力は主張しない。
- 端末での証明作成、公開記録の読取、場面生成、預託の確認が利用できることが各体験の前提。場面生成が停止しても対面後の確認と返却手続きには進める。
