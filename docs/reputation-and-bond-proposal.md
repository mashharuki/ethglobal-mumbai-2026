# 評判・没収・運営収益の検討案

2026-11-06 / **提案・未採用・未実装**。依頼は新しいルールの検討であり、この文書で既存の[資金仕様](../specs/001-private-dating/smart-contract.md)・[精算契約](../specs/001-private-dating/contracts/settlement.md)・40件の[タスク](../specs/001-private-dating/tasks.md)を変更しない。採用済みのENS → 二者照合 → 多人数候補選択を維持する。

## 結論として勧める組合せ

**評判は「安心できる人の点数」ではなく、根拠と手続きのある参加資格として扱う。没収は申告や相手の評価から直接発動せず、事前に合意した規則・証拠・裁定・異議申立てを必要とする。運営は没収額から収益を得ない。**

ハッカソンの中心実装は、参加資格の停止・回復が独立クライアントの新規検索に反映され、資金返却は妨げないところまで。金銭罰則も見せる場合は、合成の証拠と裁定fixtureによる独立した実験にする。人の嘘や勧誘を自動検出した、実世界の安全を保証した、という説明はしない。

将来の製品としては、既存のマッチ用預託とは別同意・別会計の安全保証金を比較検討する。追加の保証金が必要かは検証事項であり、額を上げれば誠実な利用者だけになるとは仮定しない。

## 現在の問題と、新しいルールの候補

| 論点 | 確認できたこと | 提案 | 根拠 |
| --- | --- | --- | --- |
| 加害側の否認 | 現行の90/10は双方が同じ虚偽を認めた場合だけ。不一致は期限返却 | 客観的証拠で判定できない対人事案には、別の裁定手続きが必要 | 現行仕様の確認＋設計提案 |
| 運営の利益 | 違反精算の10%を運営が受け取る | 罰金の運営取り分を0にする案を推奨。裁定報酬も没収額に連動させない | 現行仕様の確認＋設計提案 |
| 評判 | ENS資格の発行・停止は予定されているが、評価規則はない | 人気・成婚・マッチ回数の点数を作らず、参加状態と利用枠を管理 | 現行計画の確認＋設計提案 |
| 二重署名 | 署名の矛盾だけでは故意、訂正、再試行、端末不具合を区別できない | 自動没収の主対象にしない。無効要求の拒否、重複支出防止、再認証を優先 | 現行消費印設計の確認＋脅威分析 |
| 期限後の回収 | 返却や正常精算で消費されたnoteからは、後から没収できない | 返却保証を変えずに後追い没収できるとは主張しない。必要なら独立保証金 | 現行状態遷移の確認＋設計提案 |

## 1. 評判：参加状態・利用枠・審査状態を分ける

公開の星、点数、交際回数、相手からの人気、預託額を信用の代理指標にしない。既存の資格状態`eligible / suspended`を基本にし、本人向けの審査手続きと混ぜない。

| 状態・軸 | 新しいマッチング | 金銭・表示の扱い |
| --- | --- | --- |
| 新規・資格有効 | 少ない利用枠で参加可能。例として1ラウンド1候補 | 新規を「低評価」と表示しない。多額の預託で優先枠を買わせない |
| 初回確認済み・資格有効 | 通常枠。既存のK上限を使う | 規則の説明・鍵の確認・発行者の初回確認を条件候補にする。マッチ数や滞在日数で昇格させない |
| 通報を受け付けた | 通報だけでは全体の資格を停止しない。通報者は相手を即時ブロック可能 | 通報件数を公開せず、没収・返却期限の延長はしない |
| 証拠を確認中 | 審査者が具体的な再被害リスクを認めた場合だけ、期限付きで新規参加を制限できる | 暫定措置と違反確定を区別。理由・解除期限を本人へ通知し、自動更新しない |
| 規則違反が確定 | 規則に対応する期限付き停止。重大な反復は再参加前の個別審査 | 停止理由と異議申立てを本人へ提示。公開は必要最小限の資格状態のみ |
| 無効な申告・証拠不足・異議申立てで覆った | 暫定措置を解除し、現行資格を更新 | 「通報があった」だけの永久的な悪評を残さない。申告不成立だけで申告者を罰しない |

初回確認は本人性や誠実さの証明ではない。長くアプリに残るほど得をする昇格制度を避け、相手を見つけて検索を止めても不利益を与えない。

既存マッチの資金・返却権は資格状態から独立させる。ユーザー自身のブロックは相手との接触を止めるものであり、他の参加者との関係まで自動的に止める権限ではない。直接の迷惑行為に対応する通報・ブロックUIは追加機能で、現時点では未実装。

## 2. 何を没収対象にできるか

| 出来事 | 原則の対応案 | 没収の扱い |
| --- | --- | --- |
| 合わない、断る、会う意思を撤回、交際終了、退会 | 本人の意思を尊重して終了 | 対象外 |
| 未返信、通信断、遅刻、会わなかった | 再接続・取消・期限返却。必要なら利用者側でブロック | それだけでは対象外 |
| 不正な証明、旧版、再送、二重支出の要求 | 検証拒否・冪等処理・回数制限。鍵侵害の疑いは再認証 | 自動没収しない |
| 同じ最終回答への矛盾した署名 | 内容訂正、UIの再試行、鍵復旧との区別を調査 | 「二重署名だから悪意」とは判定しない |
| 年齢・職業についての意図的な虚偽 | 元の申告、当時の事実、帰属、規則を審査。ZKは自己申告との整合性まで | 裁定・異議申立て後に限る将来案。申告だけで不可 |
| 禁止した投資勧誘、詐欺的な送金要求、なりすまし | 事前に禁止行為を具体化し、送信者への帰属と文脈を審査 | 裁定・異議申立て後に限る将来案。通常の費用分担と区別が必要 |
| 証拠の捏造 | 捏造の証拠を別に審査 | 申告が通らなかったことと同一視しない |

スクリーンショットや相手の主張だけを、完全な事実証明とは扱わない。署名は発信元の根拠にはなっても、内容が真実か、意図的な欺きかは証明しない。現在のMVPに署名付きチャットや外部属性証明があるとは仮定しない。

Ethereumのslashingは検証可能なプロトコル違反を扱う設計だが、その証拠モデルを人間関係の評価へそのまま移すことはできない。EFの解説も、署名違反が不具合や事故で生じ得ることを扱っている。ここでは原理の比較に使い、過去記事の罰則額や現在のEthereum仕様を本製品へ流用しない。[EFのインセンティブ設計解説](https://blog.ethereum.org/2020/01/13/validated-staking-on-eth2-1-incentives)

## 3. 裁定手続きの候補

将来の試験運用では、金銭罰則のある利用期間・対象範囲・規則版・上限・期限・裁定者を入金前に明示する。後から規則を追加して過去の行動を罰しない。

1. 本人が非公開で申告し、対象となる接触・規則・証拠を示す。相手のENS名を知るだけの第三者が任意の保証金を拘束できないようにする。
2. 受付担当が対象期間、重複、関係者への帰属、証拠の適格性を確認する。これだけでは没収しない。
3. 相手へ反証の機会を与える。通知できなかった場合や無回答を、有罪への同意とみなさない。
4. 利害関係のない2名が、同じ規則に照らして審査する案を比較する。一致しなければ金銭没収しない。自分の案件や報酬を受け取る案件を審査しない。
5. 一次決定と根拠を当事者に示し、異議申立ての期間を置く。異議は別の担当で確認する。両当事者に手段を用意する。
6. 異議期間が終了し、必要な審査が完了した確定決定だけを、対象保証金・規則版・上限・受取先・期限へ拘束して執行する。

2名一致や多重署名は判断の正しさを保証しない。MVPでチームのテスト用鍵を複数使っても、独立した社会的裁定を実証したことにはならない。裁定者の確保、謝金、反証に必要な情報の開示、鍵侵害・結託・訂正の扱いは実運用前に解決する。

預入時に一次審査と異議審査の担当集合、利益相反の除外、交代条件を固定する。異なる2アドレスを独立した2人とみなさず、管理者が案件の途中で都合のよい審査者へ変更できる構成を避ける。別の異議審査担当を確保できなければ、金銭没収を確定しない。少額案件でも審査費用は発生するため、関係性の確認、重複排除、受付量の制限を設ける。被害申告そのものへ高額な保証金を要求する案は、初期案に含めない。

AIは申告の整理や規則候補の提示までに留め、最終的な違反認定・没収額・資格停止を単独で決めない。裁定者が私的な証拠を読む必要があるため、「運営・審査者も何も知れない」という説明はできない。

## 4. 資金：返却保証と罰則を同じ預託へ混ぜない

| 方式 | 利点 | 問題・推奨 |
| --- | --- | --- |
| 現在の双方合意90/10 | 裁定者が不要 | 否認する相手を処罰できず、運営が罰金で利益を得る。新しい抑止策としては不十分 |
| 現在の預託に一方的な没収を追加 | 入金を増やさずに済む | 即時取消・期限返却・先行精算と競合する。今回の推奨にはしない |
| 参加状態の制限のみ | 既存の返却保証を維持し、ENSデモへ接続しやすい | 金銭的補償を約束できない。ハッカソンの中心実装として推奨 |
| 独立した安全保証金 | 金銭罰則の対象・上限・期間を別に明示できる | 追加資金、手続き、プライバシー、審査費用が必要。将来設計、または独立した合成実験として比較 |

独立保証金の初期比較案は「1つの保証金に1つの対象関係・利用期間、同時に1つの裁定」。同じ関係からの重複通報は同じ案件へ集約し、同一保証金の総損失上限を固定する。対応する関係の真正性と本人の同意を検証する必要があり、架空案件の作成を許容しない。

裁定の認可対象はチェーン・契約・保証金・案件・対象主体・事前に定めた補償先・金額・規則版・裁定版・期限を含める。執行済み案件は再執行不可とし、総損失上限を保証金の存続期間全体の支払累計へ適用する。裁定の再送・訂正で支払先を差し替えない。鍵紛失に伴う補償先変更は、検証可能な別手順を設計してから扱う。

### 没収額・配分の案

- 実際の没収額は、事前合意した規則の額、保証金の残高、総損失上限の最小値以内。請求額や通報数だけで増やさない。
- **没収された部分は被害側へ100%、運営へ0%。** これは保証金全額を没収する意味ではない。没収しない残額は所有者へ戻す。申告者への外部ボーナスや評判加点は付けない。
- 例えば合成デモで10 USDCの保証金・総損失上限2 USDCなら、確定した対象違反では相手へ最大2、本人へ残り8以上、運営へ0。棄却・証拠不足・期限までに未確定なら本人へ10。**数字は検証用の仮値で、妥当な実運用額を決めたものではない。**
- 補償は上限付きであり、実際の被害額全額をカバーする保険ではない。USDC/EURCは銘柄別の原単位で扱い、額面の等価性を仮定しない。例のUSDC限定は既存の銘柄仕様変更ではない。

100/0でも虚偽申告の誘因は残る。裁定の誤りで相手の資金を得られる可能性があるからである。一方、共謀する2人が自分たちの資金を移すだけでは総資産は増えない。外部報酬・補助金・信用加点を付けると利益が生じ得るので、これらを組み合わせない。

採用する場合は、既存の90/10をこの仕組みへ無条件に上乗せせず、同じ行為への二重徴収を防ぐ移行が必要。独立保証金へ移す場合の推奨は、通常のマッチ用預託を元本返却の役割に戻し、行為への金銭罰則を保証金側に限定する。これはFR-009等の改訂を伴うため、まだ実施しない。

### 期限と返却

通報受付締切、反証・一次決定・異議申立て・最終確定の締切を、固定の`releaseAt`より前に定める。保証金開始後に通報や管理者操作で`releaseAt`を延長しない。手続きに必要な期間が残っていない新規の対象関係は受け付けない。

通知後の最低反証期間と、一次決定後の最低異議期間も固定する。一次決定が遅れてその期間を確保できない案件は没収対象外。裁定署名が揃っていても異議期間中は執行できず、適時の異議が受け付けられた場合はその最終判断を待つ。証拠追加・再送によって期限を無限に延ばさない。

金銭執行は必要な審査を終えた確定決定について`block.timestamp < releaseAt`でのみ可能。`block.timestamp >= releaseAt`は未確定・未執行分の所有者への返却を優先し、同じ残高を二重に消費しない。決定があっても取引が期限までに入らなければ没収できないため、提出と確定の余裕も必要になる。

裁定者が応答しない、異議審査が終わらない、証拠が不足する場合は、期限に未確定分を返す。既に返した資金から後追いで徴収しない。期限間際に生じた被害はこの保証金では補償できない可能性があり、加害者が遅らせて回避する余地も残る。永久拘束なし・確実な補償・遅い証拠への対応の全てを、この方式で保証しない。

無期限の異議申立てで返却を止めることも認めない。期限後の申告は参加資格の審査には使い得るが、返却済み資金への権利を作らない。既存の入金＋7日返却と未拘束取消は別のマッチ用預託のルールとして維持する。

## 5. ENS・Arkivとつなぐ際の境界

ENSの役割は、誰が現行の参加状態を更新できるかと、別クライアントがどの資格を信頼するか。**ENS自身が被害を判定したり、お金を没収したりするわけではない。** 裁定・状態発行・資金執行を分け、同じ管理者鍵へ無制限の権限を集めない。

公開資格には状態・必要な期限・規則版などだけを置く。告発内容、チャット、交際相手、裁定証拠、資金noteとの対応表は公開のENS/Arkivへ置かない。本人には暗号化した通知で根拠と異議申立て手順を渡す。証拠を誰が読み、いつ削除するかも定める。

それでも資格更新と資金取引の時刻は相関し得る。匿名noteの違反証拠を公開ENSへ結び付ける処理は、別のZK/認可設計が必要。状態だけを公開すれば匿名性が保たれる、と説明しない。金銭デモを透明な台帳で行うなら合成実験と表示し、現行の秘匿精算要件を満たしたとは扱わない。

別名の発行、鍵の交換、資格の期限切れ、クライアントの変更で停止をリセットできないよう、発行者側で主体の継続と資格の更新履歴を管理する必要がある。MVPで確かめられるのは同じ管理されたテスト主体の再発行まで。普遍的な一人一資格や、他の発行者の下での再参加防止は未解決。

Semaphoreのようなscopeごとのnullifierは、同じ登録identityによる繰返し利用の検出には使える。しかし別identityの発行まで同じ人だと分かるわけではない。導入する場合も発行時の重複対策は別に必要で、現時点では追加依存として採用しない。[Semaphore公式FAQ](https://docs.semaphore.pse.dev/faq)

## 6. 運営の収益と「出会えたら卒業できる」設計

ハッカソンでは運営手数料ゼロを仮置きする。継続運用の比較候補は、コミュニティ向け固定の運用料金や、利用者が事前に分かる固定料金。罰金・通報数・会話数・滞在時間・マッチの失敗回数に売上を連動させない。固定料金でも継続課金を望む動機は残るので、完全な利害一致とは主張しない。

交際成立は本人の意思で検索を停止でき、課金を止め、契約どおり返金される。交際の継続・破局を追跡しない。交際報告で金銭報酬や信用加点を与えると架空カップルを作る誘因になるため、採らない。「相手ができた」という自己申告を課金・没収の判定に使わない。

評価するのは滞在時間より、理解した上での登録、双方が望む候補、安心して断れること、停止/異議の処理、返却できたこと。交際成立率を把握する場合も任意の自己申告の限界を明示し、名前や相手を公開させない。

## 7. ハッカソンで示す範囲と次の判断

| 実演 | 見せること | 示せないこと |
| --- | --- | --- |
| 中心の推奨 | 根拠付きの合成ケースに従ってテスト発行者が状態を更新。独立クライアントが新規照合を拒否し、異議で覆れば回復。本人用キーでは状態を書き換えられない | 実世界の詐欺検出、独立した審査組織、一人一資格 |
| 任意の独立実験 | ローカルのテスト資金で、裁定fixture・上限・重複・期限返却を検証。採否と対象関係を事前固定 | 実際の証拠が真実であること、現行秘匿noteとの安全な統合 |
| 継続開発の判断 | 審査者、反証・異議の受付、証拠の帰属、保証金コスト、誤判定、匿名性を利用者テストで比較 | 「預託しているから安全」という保証 |

金銭実験の受入例は、確定した対象決定、証拠不足、異議で取消、異議未完了、同一案件の再送、別保証金への転用、上限超過、期限直前/ちょうど/以降、裁定者停止、既存の返却との分離。新しいローカル実験を採用する場合だけ、既存40件とは区別して担当・タスクを追加する。

採用時に先に決めるのは、(1)資格制限までを今回の範囲にするか、独立した金銭実験も含めるか、(2)審査できる具体的な違反を一つに絞れるか、(3)裁定者と異議審査者を確保できるか。金額や率はこの後に決める。今回の推奨は**資格制限を先行し、金銭罰則は必要性と裁定・返却・秘匿性の条件を満たしてから採用すること**。
